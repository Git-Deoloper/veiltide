# Open-source launch plan

## Pre-launch

Make the repository public only after auditing code and commit metadata for personal information and credentials. Use a fresh root commit if earlier history includes sensitive identifiers. Enable Actions tests and branch rules; complete cross-browser and HTTPS checks. Verify branding and trademark availability independently; a search for similar names is not legal clearance.

## Week 1 — earn confidence

- Publish one concrete demo video using only fictional log data.
- Open 2–4 beginner-friendly issues with clear acceptance criteria.
- Publish a guide explaining how to scrub logs before asking for help online, including honest limitations.
- Share where users already ask about the problem, only when that community welcomes tools. No cold mass messaging.

## Week 2 — listen, improve

- Ask a small number of developers to test their own synthetic examples and report missed categories privately.
- Add regression tests for each confirmed issue, without collecting real secrets.
- Measure only public repository interest and aggregated hosting performance; do not introduce tracking into the editor.
- Improve quick-start friction and deployment instructions based on feedback.

## Week 3–4 — share useful knowledge

- Write clear tutorials for GitHub issues, support tickets, and debugging handoffs.
- Publish release notes highlighting specific improvements.
- Compare the practical limitations and tradeoffs of regex masking with more comprehensive DLP systems fairly.

Never buy stars, automate follows, post repetitive promotional messages, fabricate testimonials, promise that all sensitive data will be detected, or imply an account cannot be restricted. Useful software plus earned trust is a better long-term growth strategy.
